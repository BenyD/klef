---
title: Self-hosting on Cloudflare
description: Deploy your own Klef on your Cloudflare account, with Workers and D1, and point the CLI at it.
---

Klef is one repository that deploys as one Cloudflare Worker with a D1 database. The web app, the API and these docs ship together. Hosting it yourself is a first-class use case, and the zero-knowledge guarantee holds the same way: as the operator, you can see workspace, project and file names and ciphertext, and nothing else.

## What you need

- A Cloudflare account. Workers and D1 are both available on the free plan.
- Node.js 22.18 or newer and [pnpm](https://pnpm.io).
- A Google OAuth client and a GitHub OAuth app. The sign-in page offers both, and the Worker reads both pairs of credentials, so create both.
- Optionally, a domain whose DNS is on Cloudflare. Without one, the Worker is served at a `workers.dev` address.

## 1. Fork, clone, install

Fork [github.com/BenyD/klef](https://github.com/BenyD/klef), clone your fork, and install:

```bash
pnpm install
```

## 2. Sign Wrangler in

```bash
pnpm exec wrangler login
```

Wrangler is a dev dependency of the repo, so `pnpm exec` runs that copy.

## 3. Create the database

```bash
pnpm exec wrangler d1 create klef-db
```

Copy the `database_id` it prints into `wrangler.jsonc`, under `d1_databases`. The binding `DB`, the `database_name` and the `migrations_dir` stay as they are.

## 4. Choose the address

`wrangler.jsonc` routes the Worker to `klef.sh` with `custom_domain: true`. Edit the `routes` block:

- **Your own domain:** put it in place of `klef.sh`. The zone must be active in the same Cloudflare account; on deploy, Cloudflare creates the DNS record and the certificate.
- **No domain:** delete the `routes` block. The Worker then answers at `https://klef-web.<your-subdomain>.workers.dev`. Change `name` in the same file if you want a different hostname.

Note the full `https://` origin. The next steps need it.

## 5. Apply the schema

```bash
pnpm db:migrate:remote
```

That runs `wrangler d1 migrations apply klef-db --remote`: every file in `db/migrations` that has not been applied yet, in order.

## 6. Create the OAuth apps

| Provider | Where | Authorized redirect URI |
| --- | --- | --- |
| Google | [Google Cloud Console](https://console.cloud.google.com/apis/credentials), Create credentials, OAuth client ID, Web application | `https://<your-origin>/api/auth/callback/google` |
| GitHub | GitHub, Settings, Developer settings, OAuth Apps, New OAuth App | `https://<your-origin>/api/auth/callback/github` |

Keep each client id and secret for the next step.

## 7. Set the secrets

Each `wrangler secret put` reads the value from the terminal, so none of them is ever committed:

```bash
pnpm exec wrangler secret put BETTER_AUTH_SECRET    # openssl rand -base64 32
pnpm exec wrangler secret put BETTER_AUTH_URL       # https://<your-origin>, no trailing slash
pnpm exec wrangler secret put GOOGLE_CLIENT_ID
pnpm exec wrangler secret put GOOGLE_CLIENT_SECRET
pnpm exec wrangler secret put GITHUB_CLIENT_ID
pnpm exec wrangler secret put GITHUB_CLIENT_SECRET
```

`BETTER_AUTH_URL` is the address people will use. Sign-in cookies are issued for it and passkeys are registered to its hostname, so changing it later invalidates every passkey.

## 8. Deploy

```bash
pnpm deploy
```

That typechecks, builds the app, prerenders the marketing pages, builds the docs into the same bundle, and runs `wrangler deploy`. Then check the Worker is up and can reach D1:

```bash
curl https://<your-origin>/api/health
```

It answers with `"ok": true` and `"db": { "reachable": true, ... }`. Open the origin in a browser, sign in, and create your vault.

## 9. Point the CLI at it

The CLI talks to `https://klef.sh` unless `KLEF_API_URL` says otherwise. Set it wherever you run klef, for example in your shell profile:

```bash
export KLEF_API_URL=https://<your-origin>
klef login
```

The token and the remembered vault key are kept per server, so one machine can use klef.sh and your instance side by side by switching the variable. `klef status` shows which server it is talking to. Everything else works the same.

## Updating

Pull the upstream changes into your fork, then apply any new migrations and deploy again:

```bash
pnpm install
pnpm db:migrate:remote
pnpm deploy
```

Stored data never needs re-encrypting: every blob carries a format version, and newer code reads older versions.

## Running it locally

```bash
pnpm install
cp .dev.vars.example .dev.vars     # fill in the six values from step 7; BETTER_AUTH_URL is http://localhost:5173
pnpm db:migrate:local
pnpm dev                           # http://localhost:5173
```

One dev server runs the web app and the Worker against a local D1. Add `http://localhost:5173/api/auth/callback/google` and `http://localhost:5173/api/auth/callback/github` as redirect URIs on the OAuth apps, or make separate ones for development. The docs are not part of `pnpm dev`, so `/docs` is a 404 there; `pnpm docs:dev` serves them on their own.
