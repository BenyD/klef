---
title: Syncing .env.local and .env.production
description: The everyday loop, keeping a repo's env files and the vault in step with klef sync.
---

The common setup is one project per repo, with `.env.local` for development and `.env.production` for production. This guide keeps both in step with the vault on every machine.

## Link the repo once

If you have not already, run setup from the repo root:

```bash
npx @klefsh/cli setup
```

Linking writes `.klef.json`. When the project has `.env.local` and `.env.production`, in the vault or on disk, both are recorded, so every later command covers both:

```json
{
  "workspace": "personal",
  "project": "my-app",
  "file": ".env.local",
  "environment": null,
  "files": [
    { "file": ".env.local" },
    { "file": ".env.production" }
  ]
}
```

**Commit `.klef.json`.** It holds names only, and it is how a new machine knows what to restore. **Do not commit the env files.** Make sure your env files are in `.gitignore` before the first pull. The agent instructions `klef setup` writes tell an agent to check this too.

### Files that live elsewhere

A monorepo, or a vault file whose local name differs, gets a `path`:

```json
"files": [
  { "file": ".env.local" },
  { "file": ".env.production" },
  { "file": "mobile.env.local", "path": "apps/mobile/.env.local" }
]
```

`file` is the name in the vault; `path` is where it lives on disk, relative to the repo. Paths must stay inside the directory: absolute paths and `../` are refused.

### Monorepos

`klef scan` lists env files in the checkout that `.klef.json` does not list yet, and warns about any git does not ignore. Add one with `klef link --add`:

```bash
klef scan
klef link --add apps/web/.env.local   # synced as web.env.local
```

## Sync

```bash
klef sync
```

For each file in `.klef.json`, `sync` decides on its own:

| Local file | Vault | Result |
| --- | --- | --- |
| Edited here since it last matched | Unchanged | **Push** a new version |
| Untouched since it last matched | Changed | **Pull** over the local copy |
| Changed | Changed | **Conflict** |
| Exists, never synced on this machine, differs | Any | **Conflict** |
| Exists | Has no such file | **Create** it in the vault |

A push asks first; `klef sync --yes` answers for you. A conflict stops the whole run before anything is written to either side, and exits 5. `sync` prints which keys differ, by name and never by value, and the two commands that settle it: pull the vault's copy over yours, or push yours over the vault's. Because every push is a new version, choosing push loses nothing; the old version stays in the history.

```console
$ klef sync
.env.local       edited here and changed in the vault
.env.production  in sync

.env.local against the vault:
  ~ PORT        value differs
  ~ STRIPE_KEY  value differs
✗ 1 file needs a decision. Nothing was written.
  Keep one side of each, then sync again:
  Run: klef pull --file .env.local  (take the vault's .env.local)
  Run: klef push --file .env.local  (keep this .env.local)
```

`klef status` shows the same states without the passphrase, from what this machine last synced: in sync, edited here, changed in the vault, missing here.

### How sync knows what changed

Each machine keeps `~/.config/klef/sync-state.json` (mode `0600`). For each local file it records the vault version the file last matched, and the file's modification time and size at that moment. Not a hash of the contents: a hash of a short env file would be a guessable fingerprint of its values, and "edited since?" needs only the time and size.

### Merging instead of choosing a side

A conflict offers to keep one side whole, which drops any key only the other side has. When both sides added keys, merge them by key instead:

```bash
klef sync --merge --dry-run   # what each side would gain
klef sync --merge
```

On a first sync on this machine, each side gains the keys only the other has. After that, the merge is three-way, against the version this machine last synced: whichever side changed a key wins, and a key one side deleted stays deleted. A key whose value differs on both sides still stops the merge, by name. Settle it with `klef set NAME`, which prompts you for the value, then merge again.

### Bringing back one key

If a whole-file push already dropped a key, take it back from an earlier version, without touching anything else:

```bash
klef list --versions                            # newest first: ids and dates
klef recover PROBE_GALLERY_ID --from 3f9a2c1b   # into the local file
klef push
```

## Checking without syncing

```bash
klef diff --all
```

`diff` compares each local file with the vault by key and writes nothing. A line looks like `~ API_KEY  value differs`: the key's name, never its value. With `--exit-code` it exits 10 when anything differs, for scripts. `klef sync --dry-run` shows what sync would do and does none of it.

## Pulling and pushing by hand

```bash
klef pull --all   # write every linked file from the vault
klef push --all   # upload every linked file as a new version, one confirmation
```

`pull` writes each file with mode `0600` and reports a count, such as `✓ Wrote 14 variables to .env.local`. `push` shows what changed, by count, and asks before uploading; `--yes` skips the question. Where nobody can answer it (a script, CI, an agent), push stops with the command to rerun with `--yes` instead of waiting.

## Unlock once per device

Every command that encrypts or decrypts needs the key. Approve `klef login` in the browser with **Also unlock the CLI on this device** ticked, or run `klef unlock` once, and the CLI keeps the key in your OS keychain: no command on this device asks for the passphrase again.

```bash
klef unlock          # if the browser did not unlock this device
klef unlock --for 8h # only for a while, held in memory
klef lock            # forget the key on this device
```

See [Staying signed in and unlocked](/docs/concepts/sessions/#the-cli-unlocked-once-per-device).

## Editing in the web app

Changes made at klef.sh are new versions like any other. The next `klef sync` on each machine pulls them, as long as the local file has not been edited there in the meantime.
