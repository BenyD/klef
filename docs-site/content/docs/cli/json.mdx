---
title: JSON output and exit codes
description: The --json envelope every klef command prints, its error codes, and what each exit code means.
---

Every command takes `--json`. It then prints exactly one JSON object on stdout, whether it succeeded or failed, and nothing else there. Anything meant for a person (hints, progress, the login code) goes to stderr, which a script or an agent can ignore. `klef help json` prints this summary in the terminal.

## The envelope

On success:

```json
{
  "schema": 1,
  "ok": true,
  "command": "pull",
  "data": { "files": [ { "file": ".env.local", "path": ".env.local", "variables": 14, "version": "0f3c..." } ] },
  "warnings": []
}
```

On failure:

```json
{
  "schema": 1,
  "ok": false,
  "command": "pull",
  "error": {
    "code": "locked",
    "message": "The vault is locked, and only a person at a terminal can unlock it.",
    "hint": "Ask the user to run this in their own terminal, then retry:",
    "next": [ { "command": "klef unlock" } ]
  },
  "exit": 4,
  "warnings": []
}
```

- **`schema`** changes only for a breaking change. New fields are not one, so ignore fields you do not know.
- **`command`** is the command that ran, by its full name (`list` for `klef ls`).
- **`data`** is the command's result. Each command's shape is on [Commands](/docs/cli/commands/) and in `klef help <command>`. A failure can carry `data` too: what the command found before it stopped, such as the keys behind a `sync` conflict.
- **`error.code`** is from the fixed list below. Act on it, not on `message`, whose wording can change.
- **`error.next`** holds commands to run as they are, each with an optional `description`. They are built for how you invoked the CLI (`klef` or `npx @klefsh/cli`), and none of them ever carries a value.
- **`exit`** is the process's exit code, repeated for convenience.
- **`warnings`** are `{ code, message }` objects for things worth knowing that did not stop the command.

No value is ever in the output, in any field.

## Error codes

| Code | Means | Exit |
| --- | --- | --- |
| `usage` | Unknown command or flag, or a bad value | 2 |
| `confirmation_required` | A yes was needed and nobody could give one. Ask the user, then run `next` (the same command with `--yes`) | 2 |
| `unsafe_path` | A path outside this directory | 2 |
| `not_signed_in` | No token on this machine | 3 |
| `token_rejected` | The token expired or was revoked | 3 |
| `locked` | The vault is locked; a person must run `klef unlock` | 4 |
| `no_terminal` | A person must do this at a terminal | 4 |
| `wrong_passphrase` | The passphrase did not unlock the vault | 4 |
| `conflict` | Both sides changed, or `restore` left checkouts for `sync`; nothing conflicting was written | 5 |
| `not_linked` | No `.klef.json` here, or no linked checkouts under a directory | 6 |
| `not_found` | No such workspace, project or file, or nothing to pull | 6 |
| `no_vault` | The account has no vault yet | 6 |
| `network` | The server could not be reached | 1 |
| `server` | The server refused or failed | 1 |
| `unsupported` | Not available on this platform | 1 |
| `internal` | Anything else | 1 |

## Exit codes

The same with or without `--json`, and stable across minor versions. `klef help exit-codes` lists them.

| Code | Meaning |
| --- | --- |
| 0 | Success, including nothing to do |
| 1 | Failure: network, server, or something unexpected |
| 2 | Usage error, or a confirmation was needed and nobody could answer |
| 3 | Not signed in, or the token was rejected |
| 4 | Locked: the passphrase is needed and there is no terminal |
| 5 | Conflict: both sides changed; nothing was written |
| 6 | Not found: not linked here, or no such workspace, project or file |
| 10 | Differences found, only with `--exit-code` (`diff`, `audit`) |
| 130 | Interrupted (Ctrl-C) |

Declining a confirmation at the terminal exits 1 and writes nothing.

## For agents

`klef status --json` is the call to start with. It never needs the passphrase and reports the account, the link, whether the vault is unlocked, each file's sync state, and `next`:

```json
{
  "schema": 1,
  "ok": true,
  "command": "status",
  "data": {
    "version": "0.5.0",
    "server": "https://klef.sh",
    "account": { "signedIn": true, "email": "you@example.com", "tokenSource": "keychain", "tokenStatus": "valid" },
    "vault": { "unlocked": false, "locksInSeconds": null, "problem": null },
    "project": { "workspace": "Personal", "project": "lensdrop", "config": ".klef.json" },
    "files": [
      { "file": ".env.local", "path": ".env.local", "local": true, "inVault": true, "state": "edited-here" },
      { "file": ".env.production", "path": ".env.production", "local": true, "inVault": true, "state": "in-sync" }
    ],
    "next": [
      { "command": "klef unlock", "description": "a person types the passphrase once" },
      { "command": "klef sync", "description": "bring the files in line" }
    ]
  },
  "warnings": []
}
```

Then, in short: run what `next` says; on `confirmation_required`, ask the user and run the `next` command (which adds `--yes`); on `locked`, ask the user to run `klef unlock` in their own terminal and wait; on `conflict`, show the user the key names in `data` and let them choose. `klef sync --dry-run --json` shows what a sync would do without writing anything. See [Using Klef with Claude Code and Cursor](/docs/guides/coding-agents/).
