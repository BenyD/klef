---
title: klef run
description: Run a command with the vault's variables in its environment, no .env on disk, and every secret value redacted from its output.
---

`klef run` starts a command with the variables from an env file in the vault, without writing that file to disk. The file is decrypted in memory, its variables are put into the command's environment, and the command's output passes back through klef, which replaces every secret value it finds with `[klef:redacted]`.

```bash
klef run -- npm run dev
klef run --file .env.production -- node build.js
klef run --all -- pnpm test
```

It exists for the one gap `pull` leaves: once the file is on disk, anything that can read the working directory can read it, including the coding agent that ran `klef pull`. With `run`, there is no file, and a key the app prints on the way (a framework that logs its config, a stack trace that includes a URL with credentials, a test that dumps `process.env`) reaches the terminal, the log and the agent as a marker.

## What it does

1. Resolves the linked project from `.klef.json`, like `pull` and `sync`.
2. Fetches the current version of the linked file (or the one `--file` names, or with `--all` every listed file) and decrypts it in memory. If this device is not unlocked, it stops with `locked` (exit 4) before starting anything; see [Unlocking](/docs/concepts/unlocking/).
3. Parses the file the way dotenv, Next.js and Vite do: quotes removed, `\n` expanded inside double quotes, an unquoted value cut at `#`, a quoted value allowed to span lines, the last of a repeated key winning. With `--all`, files are merged in the order `.klef.json` lists them, and a later file wins a shared key.
4. Starts the command with those variables merged over the current environment. **The file wins**: a variable set in your shell is replaced by the file's value, as if the file had been exported.
5. Forwards the command's stdout and stderr with every value from the file replaced by `[klef:redacted]`, and exits with the command's exit code.

Nothing is written to disk at any point. The variables exist in klef's memory and the command's environment, and nowhere else.

## Flags

| Flag | Does |
| --- | --- |
| `--file <name>` | One env file in the vault, by name (default: the linked file) |
| `--all` | Every file listed in `.klef.json`, merged, the later file winning |
| `--no-redact` | Forward the output as it is, values included. Prints a warning |

Everything after `--` is the command and its arguments, untouched. Flags for klef go before the `--`; flags after it belong to the command. The `--` can be left out when the command's name comes first: `klef run npm run dev` works, since klef stops reading its own flags at the first word that is not one.

## Redaction

Every value from the file is replaced in the output, on both streams, wherever it appears: on its own, inside a longer string, or several times on one line. Output is forwarded a line at a time, and a value split across two reads of the pipe is still caught. A line with no newline after it (a prompt, a spinner) is forwarded after a short pause rather than held.

Two kinds of value are left alone, because masking them would wreck the output without protecting anything:

- Values shorter than 5 characters: `1`, `true`, a port number.
- A short list of settings that are never secret, whatever their case: `true`, `false`, `null`, `undefined`, `development`, `production`, `staging`, `test` and `localhost`.

Everything else in the file is treated as secret, including values that are not (a region name, a public URL), because klef cannot tell the two apart and the safe mistake is to mask too much. A redacted value that was not secret costs a glance at the file; a secret value that was not redacted is in a transcript.

Because the output is piped through klef, the command does not see a terminal on its stdout and stderr. Most tools then turn colour off and some change their layout. `--no-redact` gives the command the terminal back, at the cost of the masking, and warns on stderr every time. stdin is always the command's own, so interactive prompts work either way.

## Exit codes and signals

The exit code is the command's: `klef run -- pnpm test` fails when the tests fail. A command ended by a signal exits 128 plus the signal number, as a shell would. Ctrl-C and SIGTERM sent to klef are passed on to the command, and klef waits for it to finish.

klef's own exit codes apply before the command starts: `locked` (4) when the device needs unlocking, `not_linked` (6) when there is no `.klef.json`, `not_found` (6) when the file has no saved version, and a usage error (2) when no command is given or it cannot be found.

## JSON

Under `--json` the command's output goes to stderr, redacted, so stdout still carries exactly one object:

```json
{
  "schema": 1,
  "ok": true,
  "command": "run",
  "data": {
    "files": [{ "file": ".env.local", "variables": 12, "version": "a1b2c3d4" }],
    "exitCode": 0,
    "redactions": 3,
    "redacted": true
  },
  "warnings": []
}
```

`exitCode` is the command's, and klef exits with it too. `redactions` counts the values replaced. With `--no-redact`, `redacted` is `false` and the warning is in `warnings`.

## For coding agents

The instructions `klef setup` writes tell the agent to prefer `klef run -- <command>` over `klef pull` whenever it needs to start the app, run the tests or run a script, and to pull only when a tool really needs a file on disk. A rule that stops an agent reading `.env` does nothing about what the app prints: a key logged at startup, or in a failing test, lands in the agent's context all the same. `run` is the wrapper that catches it on the way out. See [Using Klef with Claude Code and Cursor](/docs/guides/coding-agents/).

What `run` does not cover: a tool that reads `.env` itself and cannot take variables from the environment (some test runners and ORMs with their own loaders). For those, `klef pull` is still the way, with the file gitignored.
