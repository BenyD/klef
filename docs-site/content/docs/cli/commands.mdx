## Get started

### klef setup

Runs every step a repo needs and skips the ones already done, so it is safe to rerun: sign in, link this directory to a project, write instructions for Claude Code and Cursor, unlock, and pull the files that are not on disk yet. It ends with a names-only `klef audit` of the deploy platforms set up here, as one line of counts per scope; a platform whose CLI is missing or signed out is left out.

```bash
klef setup [claude|cursor|claude-md|agents|all] [flags]
```

Naming targets only writes the agent instructions: a Claude Code skill (`claude`), a Cursor rule (`cursor`), a block in `CLAUDE.md` (`claude-md`) or `AGENTS.md` (`agents`). See [Using Klef with Claude Code and Cursor](/docs/guides/coding-agents/).

| Flag | Does |
| --- | --- |
| `--workspace <name>` | Link to a project in this workspace |
| `--project <name>` | Link to this project, without the menu |
| `--global` | Install the Claude Code skill for every project, in `~/.claude`. Goes with `claude` or `claude-md`: `klef setup claude --global` |
| `--paste` | Sign in by pasting a token instead of the browser |

```bash
klef setup                               # everything, step by step
klef setup --project lensdrop --yes      # no menu and no questions, for an agent
klef setup claude cursor                 # only (re)write the agent instructions
```

The four steps print as they go. A step already done is reported, not repeated:

```console
$ klef setup
1/4  Signed in as you@example.com
2/4  Linked to Personal / lensdrop (2 files)
     Wrote .klef.json: names only, safe to commit.
3/4  Instructions for Claude Code and Cursor
     create   ./.claude/skills/klef/SKILL.md
     create   ./.cursor/rules/klef.mdc
     They teach coding agents here how to use Klef: commands and rules, never a value. Safe to commit.
Write 2 files? [y/N] y
     ✓ Wrote 2 files. New agent sessions pick them up
4/4  Pull .env.local, .env.production
✓ Already unlocked on this device
klef lock forgets the key here.
✓ Wrote 14 variables to .env.local
✓ Wrote 9 variables to .env.production
     .env.local       in sync
     .env.production  in sync
klef sync keeps them in line with the vault from now on.

Deploy platforms (names only)
  Vercel Development: names match
  Vercel Production: 1 only there
klef audit lists the names.
✓ Done. New Claude Code and Cursor sessions in this repo already know how to use Klef
```

Step 4 pulls only the files that are not on disk yet, so a local edit is never overwritten; when every file is on disk it says so and pulls nothing. If the browser sign-in did not unlock this device, step 4 asks for the passphrase at the terminal.

It ends the way `klef status` would: each file's state (in sync, edited here, changed in the vault; "on disk, not yet compared" for a file this machine has never synced) and, under `Next`, the commands to run (`klef diff --all` for files not yet compared, `klef sync` for files out of line). Then one line of counts per deploy platform scope, as `klef audit` would report it; a platform not set up here, or whose CLI is missing or signed out, is left out.

Without a terminal it stops at each choice: `confirmation_required` with `--workspace`/`--project` to rerun with when the project is ambiguous, or the same command with `--yes` before writing agent files, and `locked` when pulling needs this device unlocked, with `klef login` (for you to approve in the browser) and `klef unlock` as the ways out.

JSON `data`: `{ signedIn, email, linked: { workspace, project, files }, agentFiles: [ { path, action } ], pulled: [ path ], files: [ { file, path, local, inVault, state } ], next: [ { command, description } ], audit: [ ... ] }`, where `audit` holds the same entries as `klef audit --json`. Run with targets, it is `{ agentFiles }`. `action` is `create`, `update`, `unchanged` or `conflict` (a file klef did not write, left alone).

### klef login

Shows a code, opens klef.sh to approve it, and waits. On the approval page, **Also unlock the CLI on this device** (ticked by default) asks once for your passkey or passphrase and sends the vault key to this terminal, sealed so only it can open it. The CLI keeps that key in the OS keychain, so pull, push and sync never ask for the passphrase on this device. See [Unlocked once per device](/docs/concepts/sessions/#the-cli-unlocked-once-per-device).

The token is stored the same way. On its own it reaches ciphertext and names only: it cannot decrypt anything.

```bash
klef login [flags]
```

| Flag | Does |
| --- | --- |
| `--paste` | Paste a token from Settings instead, for machines with no browser. It is read from the terminal, never a flag |
| `--no-remember` | Never keep the vault key on this device. Persists until `--remember` |
| `--remember` | Keep the vault key on this device again (the default) |

```bash
klef login                  # approve in the browser, and unlock this device
klef login --no-remember    # sign in, and keep no key here
```

The code, the link and the waiting go to stderr; the result goes to stdout. A coding agent can run `klef login` too: you approve it in the browser, which is the human step, and the agent can then work without asking you for anything else.

JSON `data`: `{ email, tokenStore: "keychain" | "file", unlocked }`

### klef link

Writes `.klef.json`, which holds names only and is safe to commit. Records `.env.local` and `.env.production` when the project has them, in the vault or in the directory, so `sync`, `pull --all` and `push --all` cover both. With no arguments, lists what can be linked and exits 2. Linking again to the same project changes nothing and says so.

```bash
klef link [workspace] [project] [file] [flags]
```

| Flag | Does |
| --- | --- |
| `--workspace <name>` | The workspace, instead of the first argument |
| `--project <name>` | The project, instead of the second argument |
| `--file <name>` | The default env file, instead of the third argument |
| `--add <path>` | List one more local env file in `.klef.json` (see `klef scan`) |
| `--as <name>` | With `--add`: its name in the vault |

```bash
klef link                               # see what can be linked
klef link Personal lensdrop             # link to a project
klef link --add apps/web/.env.local     # also sync a monorepo app's file
```

`--add` names the vault file after the local one: a root file keeps its name, one in a folder gets the folder's name in front (`apps/web/.env.local` becomes `web.env.local`). It sends nothing; the next `sync` creates it in the vault.

Linking records `minVersion`, the CLI version that wrote `.klef.json`, unless the file already has one. A CLI older than that refuses to run in the repo with `outdated` and says to run `npx @klefsh/cli@latest` instead. It checks only the version it was built with; there is no network call.

JSON `data`: `{ workspace, project, file, files: [ { file, path } ], config, changed }`; with `--add`, `{ path, file, changed }`

## Everyday

### klef status

Sign-in, link, lock state and each linked file's sync state, in one call. It reads only and never needs the passphrase. Each file is `in-sync`, `edited-here`, `changed-in-vault`, `both-changed`, `missing-here`, `only-here`, `unknown` (never synced on this machine) or `absent`, worked out from what this machine last synced. Always exits 0.

```bash
klef status [flags]
```

```bash
klef status          # what is going on here
klef status --json   # the same, for a script or an agent
```

`klef status --json` is the one call an agent needs before anything else. Its `next` lists the commands that would move things on.

JSON `data`: `{ version, server, account: { signedIn, email, tokenSource, tokenStatus }, vault: { unlocked, unlockedBy: "remembered" | "agent" | null, keyStore, locksInSeconds, problem }, project: { workspace, project, config } | null, files: [ { file, path, local, inVault, state } ], next: [ { command, description } ] }`

### klef sync

Pull or push each linked file, whichever side changed. A file edited here since it last matched the vault is pushed; one changed in the vault is pulled over the untouched local copy; a file only here is created in the vault. If both changed, or this machine never synced a file that differs, nothing is written and the differing keys are listed (names, never values), exit 5. Pushes ask first. See [Syncing](/docs/guides/sync/).

With `--merge`, such a file is merged by key instead of stopping. On a first sync on this machine each side gains the keys only the other has; after that the merge is three-way, against the version this machine last synced, so a key deleted on one side stays deleted. It stops only on keys whose values differ, and suggests `klef set` for each.

```bash
klef sync [flags]
```

| Flag | Does |
| --- | --- |
| `--dry-run`, `-n` | Show what would happen, and do none of it (exits 0 even on a conflict) |
| `--exit-code` | With `--dry-run`: exit 5 when there is a conflict |
| `--merge` | Settle conflicts key by key: each side gains the other's keys |

```bash
klef sync                   # bring everything in line
klef sync --dry-run --json  # what would change, for an agent
klef sync --merge --dry-run # what a key-by-key merge would bring each side
```

JSON `data`: `{ dryRun, files: [ { file, path, action, reason, keys? } ] }`. `action` is `in-sync`, `pull`, `push`, `create`, `merge`, `conflict` or `absent`; `keys` (`{ onlyLocal, onlyVault, changed }`) is there for a conflict, and with `--merge`, `merge` (`{ conflicts, fromVault, fromLocal, removedHere, removedThere, base }`) says what each side gains. On a conflict the same `data` comes with the error.

### klef pull

Writes the vault's copy of env files here, each at mode `0600`, and reports how many variables each holds; never a value. It overwrites the local copy: `klef sync` is the safe choice when this one may have been edited.

```bash
klef pull [flags]
```

| Flag | Does |
| --- | --- |
| `--file <name>` | One env file in the vault, by name |
| `--path <path>` | Where it lives here (default: its name) |
| `--all` | Every file listed in `.klef.json` |

```bash
klef pull --all                     # every file listed in .klef.json
klef pull --file .env.production    # one file
```

With `--all`, every file is checked before anything is written, so it writes all of them or none. To run something with the variables and no file on disk, use [`klef run`](/docs/cli/run/).

JSON `data`: `{ files: [ { file, path, variables, version } ] }`

### klef push

Saves local env files to the vault as new versions. It shows what will change in line counts and asks once for all of them. Every earlier version is kept, so a push can be undone in the web app. An empty local file is refused.

```bash
klef push [flags]
```

| Flag | Does |
| --- | --- |
| `--file <name>` | One env file in the vault, by name |
| `--path <path>` | Where it lives here (default: its name) |
| `--all` | Every file listed in `.klef.json` |

```bash
klef push                 # the linked file
klef push --all --yes     # every listed file, no question (after asking the user)
```

JSON `data`: `{ files: [ { file, path, action, variables, added, removed, version } ] }`. `action` is `pushed` or `unchanged`.

### klef set

Sets one variable in a local env file, with the value typed at the terminal. The value is read with echo off from the terminal only, exactly like the passphrase: never from the command line (which `ps` shows), a pipe or a variable. So an agent cannot set a value; a person types it. Only that key's line changes (or a new line is added), and only locally: `push` or `sync` saves it to the vault. It prints `set NAME in .env.local`, never the value.

```bash
klef set <NAME> [flags]
```

| Flag | Does |
| --- | --- |
| `--file <name>` | Which env file (default: the linked one) |

```bash
klef set STRIPE_KEY                            # type the new value; nothing is echoed
klef set DATABASE_URL --file .env.production   # in another listed file
```

JSON `data`: `{ name, file, path, added }`

### klef recover

Brings one variable back from an earlier vault version into the local file, leaving every other line alone: for when a push replaced a file and took a key with it. Name the version by its id or the start of it, from `klef list --versions`. It writes only locally; `push` or `sync` saves it. The value is copied as written and never printed.

```bash
klef recover <NAME> --from <version> [flags]
```

| Flag | Does |
| --- | --- |
| `--from <version>` | The version to take it from (an id or its start) |
| `--file <name>` | Which env file (default: the linked one) |

```bash
klef list --versions                              # find the version that still had it
klef recover PROBE_GALLERY_ID --from 3f9a2c1b     # bring it back here, then push
```

JSON `data`: `{ name, file, path, version, added }`

### klef diff

Compares local files with the vault, by key, writing nothing. Each differing key is `+` (only here), `-` (only in the vault) or `~` (value differs), by name.

```bash
klef diff [flags]
```

| Flag | Does |
| --- | --- |
| `--file <name>` | One env file in the vault, by name |
| `--path <path>` | Where it lives here (default: its name) |
| `--all` | Every file listed in `.klef.json` |
| `--exit-code` | Exit 10 when there are differences |

```bash
klef diff --all              # which keys differ, and how
klef diff --all --exit-code  # exit 10 if anything differs, for scripts
```

A commented-out line such as `# STRIPE_KEY=` is reported apart from set keys, as "declared, unset" on that side, and annotates a key the other side does set (`- STRIPE_KEY  only in the vault (declared, unset here)`). Like `sync --dry-run`, `diff` is read-only: a conflict is part of its answer, so it exits 0 unless `--exit-code`.

JSON `data`: `{ files: [ { file, path, state, reason, onlyLocal, onlyVault, changed, declaredUnsetLocal, declaredUnsetVault } ] }`. `state` uses the same words as `sync`'s `action`.

### klef run

Runs a command with an env file's variables in its environment, so nothing, and no coding agent, has to open the file to use what is in it: starting the app, running the tests, a one-off query against `DATABASE_URL`. It reads the local file by default, which needs no unlock; `--from-vault` decrypts the vault's copy in memory instead, so nothing need be on disk. The command's output comes back through klef with every value from the file replaced by `[klef:redacted]`. See [klef run](/docs/cli/run/) for the rules.

```bash
klef run [flags] -- <command> [args...]
```

| Flag | Does |
| --- | --- |
| `--file <name>` | Which env file (default: the linked one) |
| `--all` | Every file listed in `.klef.json`, merged, the later file winning a shared key |
| `--only <KEY,KEY>` | Pass only these variables |
| `--from-vault` | Use the vault's copy instead of the local file (needs the vault unlocked) |
| `--no-redact` | Forward the output as it is, values included (warns) |

```bash
klef run -- npm run dev                                                   # the app, with .env.local loaded
klef run --only DATABASE_URL -- sh -c 'psql "$DATABASE_URL" -c "select 1"'  # one variable in a query
klef run --file .env.production --from-vault -- node scripts/check.js     # the vault's production values
```

- **Put the command after `--`**, so its flags are its own. klef also stops reading its own flags at the first word that is not one, so `klef run npm run dev --port 3000` works too.
- **Use `sh -c '...'` with single quotes** for a command that mentions `$NAME`. Otherwise your own shell expands it, to nothing, before klef runs.
- **The output is redacted, the exit code is the command's.** stdin is the command's own. klef prints one line of its own on stderr (`klef: 3 variables from .env.local; ...`, none with `-q`) and no value. With `--no-redact` the command gets the terminal back and its output passes through unmasked, with a warning.
- Values are decoded the way dotenv loaders read them: quotes removed, inline ` #` comments dropped. There is no `${VAR}` expansion inside the file. File values take precedence over variables already set in your environment.

Under `--json` the command's output goes to stderr, so stdout carries one object.

JSON `data`: `{ files: [ { file, source, variables } ], variables, exitCode, redactions, redacted }`. `source` is `local` or `vault`.

## Unlock

### klef unlock

Unlocks this device with the passphrase, for when the browser did not unlock it at login. The passphrase is read from the terminal only, never a flag, pipe or variable, so whatever ran klef cannot supply or see it. The key is then kept in the OS keychain, as after a browser unlock, and later commands never ask.

With `--for`, or with remembering turned off, a background agent holds the key in memory instead and forgets it after that long without use (15 minutes by default). The agent is not available on Windows yet.

```bash
klef unlock [flags]
```

| Flag | Does |
| --- | --- |
| `--for <time>` | Unlock for a while instead, held in memory: `30m`, `8h`, `7d` (at most 7 days) |

```bash
klef unlock          # unlock this device
klef unlock --for 8h # only for a working day
```

On a device that is already unlocked it says so and changes nothing. Run without a terminal, it stops with `no_terminal` (exit 4): a person has to type the passphrase, or approve `klef login` in the browser. See [Staying signed in and unlocked](/docs/concepts/sessions/).

JSON `data`: `{ unlocked: true, alreadyUnlocked, remembered, locksInSeconds }`

### klef lock

Forgets the key on this device: the one kept in the keychain, and the unlock agent's. Every command then asks for the passphrase until the next unlock or browser sign-in. Locking when already locked is fine and says so. `klef logout` forgets the key too.

```bash
klef lock
```

JSON `data`: `{ locked: true, wasUnlocked }`

## Look around

### klef list

Lists the env files in your vault, names only. Alias: `klef ls`. With `--versions`, lists one linked file's versions instead, newest first: ids and dates, nothing that needs the vault unlocked.

```bash
klef list [flags]
```

| Flag | Does |
| --- | --- |
| `--versions` | The linked file's versions instead, newest first |
| `--file <name>` | With `--versions`: another file in the project |

```bash
klef list --json        # for a script or an agent
klef list --versions    # pick a version to recover a key from
```

JSON `data`: `{ files: [ { workspace, project, file, environment, hasVersion } ] }`; with `--versions`, `{ file, versions: [ { id, createdAt, isCurrent } ] }`

### klef scan

Lists the env files in this checkout that `.klef.json` does not cover, so a monorepo app's own `.env.local` is not quietly left out of sync. It finds `.env`, `.env.*` and `*.env` (not `.example`, `.sample` or `.template`), skipping `node_modules` and build output, and says whether git ignores each: one it does not could be committed with every value in it. Paths only; no file is opened.

```bash
klef scan
```

JSON `data`: `{ linked, gitRepository, unlisted: [ { path, ignored } ], listed: [ path ] }`. `ignored` is null outside a git repository.

### klef audit

Lists the key names Vercel, GitHub Actions or Cloudflare Workers hold that your local files lack, and the reverse. GitHub secrets are compared with what `.github/workflows` references, every Worker in the repo (each `wrangler.json`, `wrangler.jsonc` or `wrangler.toml`) is audited on its own, and an environment with nothing set is one "unused environment" line. Read-only, names only, through your own `vercel`, `gh` and `wrangler` sign-ins. A platform that is not set up here, or whose CLI is missing or signed out, is reported and the rest still run. See [Auditing](/docs/guides/audit/).

```bash
klef audit [vercel|github|cloudflare] [flags]
```

| Flag | Does |
| --- | --- |
| `--exit-code` | Exit 10 when there are differences |

```bash
klef audit                  # every platform set up in this directory
klef audit vercel --json    # one platform, for an agent
```

JSON `data`: `{ targets: [ { platform, environment, label, file, compareTo, worker, status, reason, onlyOnPlatform, onlyLocal, both } ] }`. `compareTo` is `file` (a local env file) or `workflows` (GitHub, where `onlyLocal` is referenced but not set and `onlyOnPlatform` is set but never referenced). `worker` is a Worker's directory. `status` is `ok`, `no-local-file`, `empty` (nothing set there), `skipped` (not set up here) or `unavailable` (the tool failed; `reason` says why).

## New machine

### klef restore

For a new or reset machine: clone your repos, then run this once. It lists every linked checkout under the directory with the vault project each names, and asks before decrypting anything. Then it only pulls. Anything that would push, and any conflict, is left for `klef sync` in that checkout, and the command exits 5 with that `sync` as the next step. See [Restoring on a new Mac](/docs/guides/new-machine/).

```bash
klef restore [dir] [flags]
klef restore ~/Developer   # every linked repo under ~/Developer
```

JSON `data`: `{ root, projects: [ { dir, workspace, project, files: [ { path, action, reason } ] } ], problems: [ { dir, error } ] }`

## Account

### klef logout

Revokes the stored token, so it leaves the web app's token list, then forgets it and the vault key kept on this device. If Klef can't be reached, it still signs out locally and says the token is still valid; revoke it in Settings, Security, Access tokens. A token in `KLEF_TOKEN` is never revoked, since it belongs to whatever set it: klef still signs in with it, and says so.

```bash
klef logout
```

JSON `data`: `{ signedOut, revoked, tokenStillInEnvironment }`

## More

### klef completion

Prints a shell completion script. See [Shell completion](/docs/cli/#shell-completion).

```bash
klef completion <bash|zsh|fish>
```

### klef help

Shows help for klef, a command, or a topic: `json`, `exit-codes` or `environment`.

```bash
klef help [command|topic]
klef help pull   # one command
klef help json   # the --json format
```
